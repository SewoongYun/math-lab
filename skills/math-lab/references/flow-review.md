# 화면 흐름 점검 (두 모드 공통, 선택)

> 만든 HTML의 **화면과 버튼이 어떻게 이어지는지**를 간단한 화면 지도로 펼쳐, 학생이 막히는 곳·빠진 길·정답이 새는 곳을 찾는다.
> 계산이 맞는지는 원칙 3(검산 표)이 맡고, 이 점검은 **흐름**만 본다.

## 0. 필요한 것

- **wireflow-review 스킬** — JeongK7998이 만든 별도 스킬이다. math-lab에 들어 있지 않으니 [그 저장소](https://github.com/JeongK7998/wireflow-review)의 안내대로 따로 설치한다. 남이 만든 스킬이므로 설치 전에 파일을 한 번 읽어 본다.
- **Node.js 18 이상** — 흐름 지도를 만들고(`build`) 검사하는(`check`) 명령이 Node로 돈다.
- **파일을 읽고 쓸 수 있는 환경** (예: Claude Code). claude.ai 대화창처럼 파일·명령 실행이 없으면 이 점검은 하지 않고, "파일을 쓸 수 있는 환경에서 흐름 점검을 할 수 있다"고 한 줄만 알린다.

셋 중 하나라도 없으면 흐름 점검을 건너뛰고 **건너뛰었다고 말한다.** 한 것처럼 쓰지 않는다.

## 1. 언제 하나

| 한다 | 하지 않는다 |
|---|---|
| 단계가 있는 책 실험실 (`1 예상 · … · 5 정리`, 예상을 적어야 다음 단계가 열림) | 슬라이더 하나짜리 스케치 위젯 |
| 힌트 1~3단, **정답 공개(확인 창 뒤)**가 있는 시뮬레이터 | 화면이 한 장뿐인 페이지 |
| 교사용/학생용 전환, `풀었음` 체크·접기가 있는 변형 문항 페이지 | |
| 사용자가 "흐름 점검", "화면 흐름", "와이어플로우"라고 할 때 | |

- 시간이 걸리는 일이라, 위 조건의 페이지를 만들었으면 끝맺을 때 **"흐름 점검도 할까요?"라고 묻기만** 한다. 하라고 할 때 한다.
- `/math-lab 흐름 <HTML 경로>`로 불렀으면 묻지 않고 한다. 바로 HTML 모드(`html`)에서도 마찬가지로, 만든 뒤 묻는다.

## 2. 어디에 두나

HTML 옆에 `흐름 검토/` 폴더를 만들어 둔다. 학생에게 배포하는 폴더(공개 사이트 등)에는 넣지 않는다.

```
<config.md의 HTML 폴더>/
├─ <자료 이름>.html
└─ 흐름 검토/
   ├─ <자료 이름>.flow.json     원본 (고칠 때 쓴다)
   └─ <자료 이름>-흐름.html      보는 파일 (더블클릭으로 열림)
```

남기는 것은 이 **두 파일뿐**. 연습용·예제 파일은 지운다.

## 3. 순서

### F1. 화면 목록 뽑기 (만든 HTML에서)
- 실제 코드에서 **화면(단계·창·접힘 상태)과 버튼, 잠금 조건**을 옮긴다. 짐작으로 그리지 않는다.
- 같은 꼴이 반복되면(변형 1~5, Q1~Q5) 대표 하나로 묶고, 묶었다고 `review.source`에 적는다.

### F2. flow.json 쓰기
wireflow-review 스킬의 `references/flow-model.md`를 따른다. math-lab 자료에서 정한 것:

- `review.locale: "ko"`. 휴대폰 세로가 기준이므로 `device`는 생략(= mobile).
- 잠금은 `vars` + `when`으로 만든다. 예: `{"guess": false}` → 「다음 단계」 버튼에 `"when": {"guess": true}`.
- **꼭 넣을 시나리오**
  - 처음부터 끝까지 한 번 (책 실험실: STEP 1 예상이 STEP 5 정리에 다시 보이는지)
  - 되돌아가기: `← STEP k−1` 뒤에도 적어 둔 예상·슬라이더 값이 남는지
  - 정답 공개 확인 창에서 **취소** → 정답이 안 보이는지
  - 학생용 보기에서 정답·해설·교사용 칸이 **안 보이는지** (`inspect`의 `absent: true`)
  - 힌트 1 → 2 → 3 순서, 힌트 없이도 정답 공개까지 갈 수 있는지
- `review.requirements`: `sim-design.md` 6절 점검표 중 흐름에 해당하는 것 + 사용자가 말한 의도. 사용자가 말한 것은 `origin: "source"`, 클로드가 짐작한 것은 `"inferred"`.
- **원칙 2**: "무엇을 보여 줄지, 결과가 어떻게 나올지"는 교사가 정한다. 코드에서 정해지지 않았거나 클로드가 임의로 정한 것은 `decisions`에 질문으로 남긴다. 혼자 정해서 흐름에 넣지 않는다.

### F3. 만들고 검사하기
```bash
node <wireflow-review 폴더>/scripts/wireflow.cjs check "흐름 검토/<자료 이름>.flow.json"
node <wireflow-review 폴더>/scripts/wireflow.cjs build "흐름 검토/<자료 이름>.flow.json" "흐름 검토/<자료 이름>-흐름.html"
```
- `check`의 `findings`가 0이고 시나리오가 모두 통과해야 한다. 남은 문제는 고치거나, 고치지 않을 이유를 사용자에게 말한다.

### F4. 브라우저에서 확인
- 흐름 HTML을 연다. 왼쪽 위 **「흐름 검증」**에서 `통과 n · 문제 0 · 미검증 0`을 확인한다. `기획 확인 필요`의 개수는 F2의 `decisions` 개수와 같아야 한다.
- 클로드가 브라우저를 다룰 수 있는 환경이면 직접 열어 확인한다. 많은 내장 브라우저는 `file://` 주소를 열지 못하므로, 그럴 땐 그 폴더를 로컬 서버로 띄워서 연다.
- **실물 HTML도** 주요 경로 하나는 실제로 눌러 본다. 지도만 통과하고 실물을 안 눌러 봤으면 그렇다고 말한다.

### F5. (선택) 실제 화면 캡처 넣기
사용자가 "실제 화면이 안 보인다", "캡처를 넣어 달라"고 할 때. 지도는 원래 회색 상자로 흐름만 그리는 도구다.
- 실물 페이지를 상태별로 열어 캡처한다(브라우저 도구가 있을 때).
- flow.json 맨 위 `images`에 `"shot-이름": "data:image/jpeg;base64,…"`, 화면의 `visual` 블록에 `"image": "shot-이름"`과 캡처 비율에 맞는 `aspect`(`landscape`=4:3, `wide`=16:9, `square`, `portrait`=3:4).
- 캡처를 넣은 화면은 `ui.layout: "split"`을 빼서 사진이 폭을 다 쓰게 한다.
- 브라우저 기본 확인 창(`confirm`)처럼 캡처가 안 되는 화면은 그림으로 두고 그렇다고 말한다.
- 페이지가 바뀌어도 캡처는 저절로 바뀌지 않는다. 다시 찍어야 한다고 알린다.
- 캡처에 **원문항·교재 그림**이 찍혔으면 그 지도는 공개하지 않는다 (SKILL.md 6절).

### F6. 교사 검토 → 고치기
- 교사는 흐름 HTML에서 화면을 고르고 **「수정 요청 목록」에서 복사해 대화에 붙여 넣는다.**
- 붙여 넣은 요청은 flow.json의 화면·버튼 ID로 찾아 **실물 HTML과 flow.json을 함께** 고친다 → F3·F4 다시.
- `decisions`에 답을 받으면 반영하고 그 질문을 지운다. 답을 받기 전에는 지우지 않는다.

## 4. 걸려 넘어지기 쉬운 것

- `visual`의 `aspect`는 `wide` `landscape` `square` `portrait`만 된다. `"4 / 3"`처럼 쓰면 지도가 하얗게 뜨고 콘솔에 `invalid layout block`이 나온다.
- `when`은 값이 정확히 같을 때만 맞는다(부등호 없음). "마지막 문항이 아니면" 같은 조건은 `last: false` 같은 변수로 만든다.
- 애니메이션이 있는 실물 페이지는 브라우저 도구에서 느리게 그려질 수 있다. 실물 검사는 애니메이션이 끝날 때까지 기다린 뒤 상태를 읽는다.

## 5. 노트에 남기기

- 책 실험실 기록이나 문제 노트의 시뮬레이션 칸에 한 줄: `흐름 점검: 통과 n · 문제 0 · 기획 확인 k (흐름 검토/<자료 이름>-흐름.html)`. 하지 않았으면 적지 않는다.
- `decisions`에 남은 질문은 노트에도 옮겨 적는다 (교사가 정할 일).
